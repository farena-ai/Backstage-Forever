# Backstage Forever — The Field Dispatch and the Forever-only Companion

Planning baseline: [v1.11.0](https://github.com/farena-ai/Backstage-Forever/releases/tag/v1.11.0), `1b010072089ac02ba85c493510d41f112270283d`. The milestones below are proposed cuts, not promised release numbers or shipped features. This plan extends [the All-in-One roadmap](ALL-IN-ONE-ROADMAP.md), not a replacement for its game, platform, or evidence gates.

The [expansion backlog](FOREVER-EXPANSION-BACKLOG.md) ranks additional ideas for Companion, knowledge coverage, onboarding, leveling, professions, endgame, art, and platform support. This document remains the delivery plan; backlog ideas do not increase first-release scope by default.

## 1. Product outcomes

- On the first successful launch after upgrading, show one useful, beautiful **What’s New** panel: exactly which installed versions the player moved between, everything player-facing that changed in the releases they skipped, and where to try it. Make the full history available later without interrupting the game.
- Make the Companion the fastest way to get a trustworthy **WoW Forever** answer. A short direct answer, verified details, one practical next step, and an optional source disclosure beat a long confident essay. New players can ask naturally; veterans can use exact IDs, compare options, and inspect the evidence.
- **No Retail, Classic, or other ruleset as a fallback in Companion.** Clearly marked Classic reference may remain in Atlas and existing reference surfaces; it is not Companion evidence. This includes the current dungeon-prep entrance and level range when they are only Classic reference. Keep the helpful saved-quest portion; replace the unsupported part with an honest gap. No provider gets an exception.
- Preserve character privacy, offline value, the original parchment-and-brass aesthetic, and the addon’s manual-control boundaries. Do not add paid dependencies, analytics, background network requests, or live game permissions to these first cuts.

## 4. What’s New: product and state contract

**Player flow.** A first successful updated desktop launch, after journal recovery and mandatory setup decisions, shows an original illustrated **Field Dispatch**. Header: “Updated from 1.9.0 to 1.11.0” when both are known. Below: a few highlights, platform/privacy notices, and all installed-range entries grouped by version, expandable and searchable if the jump is long. Example: a 1.9.0 → 1.11.0 fixture includes 1.10.0 and 1.11.0, not 1.9.0; it includes the new desktop-only preparation behavior. Do not repeat unchanged items, but preserve a later correction or removal as a separate change. No truncation masquerading as full history; if older notes are missing, identify the gap and let the user browse the available history.

**When to show.** Use the running installed version, not download/ready state, update poll, or the tag string from an unauthenticated feed. Keep “last successful run” distinct from the acknowledgement/range ID and commit the pending range atomically before replacing the prior-run marker. If a trusted previous-version value is available for installs predating the feature, migrate it; otherwise show neutral current highlights/version history on an appropriate entry point, never invent a predecessor. Brand-new setup gets the normal welcome, no automatic upgrade popup. Restart does not re-open acknowledged notes; a crash before display must not lose them. Support Not now, explicit acknowledgement, and manual reopening. Rollback, same-version repair, and preview-to-stable promotion have separate, tested rules and must not claim unseen releases were installed. Manual Mac replacement uses the same local state where retained; moved/deleted profiles may have an unknown predecessor. No popup in an in-game overlay, combat, or background startup; defer until a foreground desktop window is ready and not showing a higher-priority recovery dialog. For addon-only users, consider a later explicit `/bf news` digest rather than a forced login interruption.

**Design and release content.** Reuse the existing art language, illustrated trim, neutral faction-safe imagery and native focus management. Use short categories: New, Improved, Fixed, Compatibility/privacy, Desktop, Addon. Full notes remain navigable and scrollable at the minimum supported size, 200% text scaling, English and compact German. Escape and focus return work; motion reduces or stops; visible actions never rely on text painted into art. Offline text is shipped and trusted with the app; optional external release link uses an allowlisted project URL and an explicit click. Maintain version/platform applicability in the index. App, addon and Mac limitations are searchable but clearly badged.

## 5. Forever-only Companion: evidence and answering rules

**Single eligibility decision.** Keys include game edition, compatible build/range plus proof of compatibility, source ID and revision, stable entity/map IDs, locale aliases, race/faction/class gates as needed, observed time and evidence kind. Separate four visible labels: **Verified for this Forever build**, **From your save** with date and character, **Historical Forever observation** with its actual build/date, and **Not verified**. Historical observations may appear as an explicitly historical answer to a historical question; they never prove current availability, route edges or live game state. Exact build is necessary for many facts but an overlapping label alone does not prove a particular loot row was seen on that build. User-reported facts may help rank or clarify; they cannot promote game facts. Unknown build admits only evidence documented as build-independent within Forever, not “unknown matches unknown.” Community evidence is quarantined until reviewed; even reviewed historical hints do not become automatic waypoints. Imported data and tool output remain untrusted as instructions.

**Strict input bands.** Use official Forever notes or sources explicitly scoped to Forever and permitted for use, licensed reviewed captured packs, and consented last-saved player evidence. Record original source, licence, actual observation date versus publication date, build set, known gaps and conflict decisions. Do not send free-form searches to the web, admit Retail URLs, use Classic clone/wikis as fallback, or round-trip unreviewed chat output back into the facts. Exact entity match plus edition and build checks come before approximate scores. Keep map/area and quest prerequisites explicit, including class/faction/phase if proven. Unknown is not zero, unavailable is not impossible, same name is not same ID, and a warning is not proof of a rule.

**Answer pipeline.** 1. Interpret the job and scope (including build/faction only when they change the answer); split mixed requests. 2. Clarify once if candidates differ meaningfully; expose short choices by label and ID. 3. Retrieve eligible facts and classify direct answer, partial answer, conflict, or no verified evidence. 4. Render an authoritative local result first where possible. 5. Only if helpful and already configured, give a model bounded, typed evidence and local tool access to explain or compare. No model access to open web, provider-native search, game actions, raw files or private data. If a transport cannot enforce those boundaries or changes tool support, fall back to the verified local answer rather than a plain ungrounded prompt. 6. Validate IDs, numbers and cited claims against allowed evidence before painting; for claims that cannot reliably be validated use evidence-backed templates, not free-form factual generation. Do not stream unverified gameplay prose. Model voice, summaries and follow-up wording are optional; factual authority stays in app code. 7. Attach approved sources by footnote/receipt or internal links built from trusted IDs. Never let a model invent links or claim a source it did not use. Tool timeouts and cancelled responses end with a local result or an honest gap, not a guess.

**Answer shape.** Direct first line; location or exact fact and what makes it applicable; next best action; expandable **Why this answer / Sources** with the build, date, evidence kind, and explicit uncertainty. Deep-link to Map, Quest Guide, Atlas, Workshop, Ledger or Sheet only when the target and context are resolved. Offer correction/disambiguation if a question assumes an unsupported Retail feature. Do not scold, ask which game this is, or silently change the subject. Say, for example: “I can match that quest to your saved log, but I don’t have a verified Forever turn-in location for this build. Open Quest Guide to review the objective you have saved.”

**Privacy and safety.** Local-only saved facts stay off provider history, saved Memory, diagnostic telemetry and clipboard until the player explicitly uses an allowed action. Keep approved sharing and preview visible, and recheck ownership immediately before reads, sends and paint, with queued/busy/switch/revoke/reload tests. Do not treat authorization, saved location or a 16-bit hash match as proof the overlay knows the current character. Until there is a separately qualified stronger protocol, private preparation remains desktop-only. No live combat decisions, input/game automation, purchases, crafting, auto-pin or other game actions; keep existing secure restrictions and consent controls.

## 6. Coverage and validation scorecard

| Area | Priority player questions | Evidence and gates |
| --- | --- | --- |
| Questing and route | “Where do I start/finish this?”, “Who drops this quest item?”, “What's next at my level?”, “What can I do if this step is missing?” | Exact quest/NPC/item/map/build. Saved objective ≠ completion. Only validated prerequisites and manual navigation. |
| NPCs, travel, training | “Where's the flight master?”, “How do I get from X to Y?”, “Who trains guns near here?” | Faction/reaction and transport legs verified independently. No invented schedules, price, fastest route, or assumed position. |
| Dungeon/raid | “Can I prepare for this run?”, “Which quests are in my log?”, “What loot is verified?” | Entrance and mechanics only from Forever evidence; references tied to their actual observations. No implied eligibility, live lockouts or personal drops. |
| Workshop, gear and reputation | “What am I short for two crafts?”, “Where can I get this exact item?”, “Why is it an upgrade?”, “What gets me to the next standing?” | Distinguish counted/stale/unknown, price observations vs present supply, class usability, and estimates from proven progress. |
| Usability | Misspellings, shorthand, links, `#ID`, natural follow-ups, new player English, compact German, wrong assumptions, no model and airplane-mode questions. | Useful first answer, a single clarifier where needed, source details available, exact destination opens, return/focus intact. |

**Test program.** Keep the existing published banks for regression; add a new frozen held-out set authored separately from the implementation. Cover both factions, levels, plausible unknowns, same-name Retail/Classic lookalikes, false premises, contradictory packs, stale saves, swapped characters, partial imports, broken links, malicious text in sources, tool refusals, and attempts to switch edition by instruction. Include actual provider-output fixtures (unsupported injected facts, fabricated citations, failed tool round, streaming tails), and record separately: routing, entity top choice, evidence eligibility, final fact correctness, abstention, action success, privacy, and latency. Do not count a grounded prompt as a correct final answer. Provisional release targets: zero wrong-edition evidence or unsupported factual claims in the negative regression suite, zero private data boundary failures, no regressions in the tagged banks, at least 95% correct actionable answers on a new held-out set of answerable questions in supported launch domains, and separately measure correct abstention and false refusals. Pin size and cases before scoring; report counts/denominators and per-domain breakdown. Set local response p50/p95 budgets from representative tagged warm/cold runs, and measure first useful card separately from optional model time. Passing a finite corpus is not a guarantee against every possible question. No paid model evaluation without approval; offline and stubbed tests are mandatory, real-provider quality remains separately qualified.

**Ship checklist.** Re-run applicable existing CI gates, generated catalogs/locales and actual Electron smokes. Exercise known version jumps, installed upgrade and rollback in isolation when available, verify the signed public manifest with the prior stable client, and report Windows/macOS/addon limitations. Inspect normal and compact screenshots/focus. Real WoW hands-on, native Mac, two-player party, real provider and community/operator acceptance stay explicitly outstanding until performed; none are inferred from fixtures. Data provenance and privacy are stop-ship gates; if coverage is insufficient, narrow the feature rather than weaken the checks.

**Release custody.** Before publication, bind the candidate to its exact source tree and staged artifact hashes. Verify timestamped Windows Authenticode and the signed update manifest against the previous stable client. Verify each macOS app's signature before making its ZIP public; distinguish ad-hoc integrity signing from Developer ID signing and notarization. The standalone addon and source ZIP are not OS executables; verify their tagged-source parity and bind their exact digests in the release receipt. Hold any artifact that cannot satisfy its applicable signing or integrity gate; a local build or a successful upload is not proof of publication. Use existing infrastructure without adding a paid service or new workflow by default.
