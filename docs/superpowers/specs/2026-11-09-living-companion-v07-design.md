# 0.7 Living Companion design

## Outcome and chosen approach

The player can prepare the companion with one primary action, start playing, and receive useful changing quest guidance inside WoW without reloading after every objective, level or zone change. Desktop character switching/imports remain reliable when game saves arrive. AI stays optional.

Compared approaches: desktop-only planning retains save friction; a continuous desktop bridge has no verified supported full-character transport; a local in-game planner uses supported game events now. Choose the third. The desktop prepares resources, maintains saved profiles and provides optional AI. The addon plans locally from public current-character observations and a bundled source-labelled reference slice. No continuous desktop feed is promised.

## Boundaries

- No movement, targeting, combat decisions, automated interaction, macros, forced reload/logout, memory reads, protected-value bypass, unsolicited messages or paid background inference.
- Keep 0.6.1 pre-login/logout lifecycle repair, per-character stable identities, private journals, deliberate selection/follow preference, profile cap 100, bounded capture and all cancellation/reset epochs.
- Native guidance updates out of combat; combat hides it and defers reads until safe. Unsupported/protected APIs stay unknown.
- A newly installed/updated addon loads at the next game login/restart, or a voluntary UI reload if supported. Do not instruct repeated reloads for routine play. Desktop freshness stays explicitly last-saved.
- No OS service, scheduled task, release watcher or background process outside the running app. No new account link is required. Process metadata checks stay local and do not read game memory.

## A. Bundled in-game planner and reference

Add `BackstageForeverReference.lua` generated deterministically from the existing validated pinned `data/forever/pack.json`, and a pure `BackstageForeverPlan.lua`. Do not copy third-party addon code. The reference contains only bounded quest identity/title and the small location/NPC facts needed by the planner, build/locale/source/attribution; no player data. Lua string escaping must prevent data from becoming executable code. Generation must be reproducible offline, <=1 MiB per managed file, with attribution/CC BY link, source commit, compilation-change and Blizzard-rights notice in the generated header. Pin generated bytes to LF. Runtime public reference refresh does not generate/evaluate Lua.

Load order: reference, planner, capture, HUD. Five owned files including the TOC are installed/read back/repaired; unrelated files remain untouched.

Pure interface:

`BackstageForeverBuildPlan(character, options?) -> {status, headline, steps, counts, reference}`

Options focus `balanced|nearby|turn-ins`, minutes `15|30|60` (card count preference, never invented travel duration). At most three native steps, deterministic stable order. A step has `questId`, `phase` (`t|o`), `title`, `detail`, `source` (`game|reference|none`), optional `destination={mapId,x,y,text?}`, and optional `command` only when current identity/build/phase/coordinates make the existing explicit guide command valid. Public snapshots are already guarded, but the planner must bound/type-check inputs and gracefully reject malformed reference/player fields.

Ready turn-ins precede unfinished objectives in balanced mode; nearby favours same-map known points without treating cross-map Euclidean distance as a route; turn-ins only shows ready quests. Current game titles/objectives/markers are authoritative. Reference destinations require exact build, ID and compatible title (a localized current title stays authoritative with qualified English reference). Actual game points win. Mark community positions approximate. Never use a mere NPC mention as a quest giver/finisher. No hard prerequisite/availability claims or borrowed data on another build. Missing objective details produce an honest useful check-quest step, not an invented target or an empty promise.

The compiler may pre-resolve bounded reference destinations using the existing KnowledgeIndex semantics; pure Lua must still enforce current phase/build/title and current game priority. No full route/travel graph or new data-source expansion in 0.7.

## B. Living native Compass

Extend the native WoW-styled draggable/collapsible/hideable panel to show the current character, compact XP/quest state, up to three next steps with source labels, a focus control and an explicit `Show waypoint` button for the first supported destination. The button calls the existing guarded guide function from a genuine click; it never opens a game map or moves the player. Invalid/missing markers show a clear disabled state. Preserve native textures, permanent hide/show instructions and keyboard/contrast readability.

Persist focus/session preference in existing per-character HUD settings without losing anchors/visibility. If the planner/reference is missing, keep basic capture/HUD usable. Add a bounded feature-detected event coalescer (approximately 250 ms) for bursts if supported, with immediate login/world-entry/level/turn-in/combat-end refresh. Queued callbacks must carry a lifecycle generation and cannot run after logout or mutate a later character. If timer APIs are unavailable, use the guarded immediate path. Never defer the only prepared export into logout teardown. No frame-by-frame polling or background AI. Existing Lua large-roster deadline/bounds remain.

## C. Setup and saved character backend

Add a narrow local game-runtime helper: tri-state `running|not-running|unknown`, checked time, and safe launch of the configured client's literal `Wow.exe` only on the player's button press. Windows probes use bounded hidden, fixed-argument OS process metadata and compare executable paths to the validated game folder; no command line/account data or full process dumps reach the UI. Unknown/failure must not block setup. Non-Windows degrades safely. Cache probes for >=15 seconds; inject probe/launch runners in tests. Validate game/executable paths and refuse symlink/junction ancestors; no renderer-supplied launch executable/arguments/URL, shell command interpolation or authentication automation.

Add IPC `startCompanion()` returning the ordinary gameSnapshot shape plus `setupCandidates` when multiple installs need a choice. Existing connected folder is repaired. Exactly one validated discovery candidate is prepared automatically. Zero/multiple candidates do not silently choose a folder or automatically open a picker; the UI offers a simple choice or existing native folder picker. Preserve gameAction/subscription/reset/disconnect generations across every await. Add `launchGame()` with no arguments, using only the current validated root; successful process creation means launch requested, not proven game load.

Game status gains additive `runtime`, `loadedCaptureVersion`, and `companionState` fields, distinguishing prepared files, next-login/update needed, last saved imported data and unavailable folder. Running/closed/unknown state changes friendly action text. Existing phase/check compatibility can remain. Do not claim the addon is loaded merely because files were installed; old on-disk capture versions are evidence about the last save only.

Read all valid bounded account exports rather than only the newest account file. Combine newest per-character observations deterministically, select the latest saved active character, deduplicate, and retain at most 100 characters (always retain latest active). Report partial/omitted coverage if necessary; malformed/transient files cannot erase good profiles. Publish one validated composite snapshot per changed digest, with stable ordering and generation checks. Respect per-character timestamps and explicit manual selection/follow-off; older account data must not roll back newer fields, journals or active selection. No account paths/identifiers enter AI/public exports. No account-wide discovery of never-visited characters is claimed.

## D. Beginner frontend

First run has one clear `Start my adventure` action. Once files are prepared, the player may enter the app/play without needing a desktop snapshot or an AI provider. If game is closed, offer `Open Forever` when the validated executable is available; otherwise explain ordinary launcher use. If already running, offer quiet next-login activation and an optional copyable reload instruction; never force interruption. Multiple installs use readable choice cards; no-path discovery offers one folder button.

Separate `Prepared for next login`, `Live guidance runs in WoW`, and `Desktop last saved …` in plain language. Healthy setup stays quiet. A stale desktop snapshot is not a broken live companion. Remove routine level/zone-change reload nags across Adventure, Game Connection and Field Guide. Refresh desktop remains an optional explicit action with honest save semantics. Reopening setup remains possible. Existing native dark dropdowns, original faction/class art, focus, compact 1000x700/reduced-motion accessibility and autosave are preserved.

## Acceptance

Offline compiler reproduction and adversarial escaping; Lua planner actual/reference/missing/build-conflict/localization/focus/marker guards; event burst/lifecycle/character-switch and HUD persistence/combat tests; five-file transactional readback/repair; setup no/one/multiple roots and running/closed/unknown states with cancellation/reset races; multi-account snapshots with different timestamps, bad/partial files and follow preference; real Electron first-run/setup/switching/compact/autosave/integration/Quest Guide; full unit, rebuilt package source/resource hashes, independent task/final reviews, signed CI publication and public download verification. All automated play data is synthetic. Real game load/new live guidance remains player-led acceptance, distinct from fixtures.

Self-review: scope is achievable live local guidance and lower-friction setup; no new desktop live transport, external account API, complete travel graph, class simulator or automatic inference is implied.
