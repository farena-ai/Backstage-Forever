# 0.10 Preparation and Professions

## Outcome and verified API choice

Provide a graphical preparation workshop using the player's actually observed professions, known recipes and carried materials. Calculate recipe shortfalls locally, show other characters' dated observations and create a manual shopping checklist deliberately. Compared approaches: a third-party crafting database has uncertain build/license provenance; manual-only entry misses the automation goal; guarded current-player client observations provide useful supported facts. Choose client observations with explicit partial/unknown states and manual fallback. Do not promise vendors, drop locations, skill-up paths or gear improvements without separate verified data.

Research: work/series-data-research.md and exact-build generated API references under work/series-data-research/. Primary mirror pin https://github.com/Gethe/wow-ui-source/tree/9dc84f0d3bbae1768ac3405b3716000bd93eda06 is titled Forever 1.60.1 (70862). Research files are not runtime dependencies; independently implement calls, do not redistribute Blizzard UI implementation. C_SkillInfo.GetSkillLineInfo returns a table. C_TradeSkillUI.GetProfessionInfoBySkillLineID maps owned skillLine IDs to profession metadata; GetProfessionSpells(professionID,skillLineID) returns known spell IDs. Use GetRecipeInfo/GetRecipeSchematic and learned identity checks. GetAllRecipeIDs is absent in this build and cannot be the only collector. Feature-test/guard all calls. No UI opening, header/filter changes, linked/guild adoption, crafting or item use.

## Observation schema and ownership

Extend optional `readiness.workshop`, keeping equipment/bags and root schemaVersion1. New pure `preparation-data.cjs` owns strict validation and capture timestamp normalization, with no root-validation dependency. `validateWorkshop(undefined)` returns undefined. Exact allowed keys:

```text
workshop = {professions?, recipes?, materials?}
collection = {observedAt:canonical ISO UTC, complete:boolean, items:[]}
professions.items <=20: {skillLineId,professionId,name,rank,maxRank}
recipes.items <=100: {id,skillLineId,name,reagentsKnown:boolean,reagents:[],outputItemId?,outputMin?,outputMax?,canSkillUp?}
recipes.reagents <=20: {itemId,required,name?}
materials = {observedAt,complete,scope:'bags-0-4',items:[]}
materials.items <=256: {itemId,count,name?}
```

Positive IDs are integers 1..2147483647. Counts/ranks/outputs are integers, ranks0..10000 with rank<=maxRank; outputMin/Max1..10000 with min<=max when both exist; material counts1..1000000 and reagent required1..100000; names nonblank <=200 chars, no ASCII controls. Unique IDs within each collection and reagent item IDs per recipe; every recipe skillLineId must be a valid positive ID (absence of a current profession makes planning unavailable, not an automatic reassignment). Booleans are actual booleans. Strict unknown-key rejection, detached output. `reagentsKnown:false` requires empty reagents; a successful unambiguous genuinely reagent-free recipe may have true/empty. Optional/alternate/variable/non-item required slots are not silently collapsed into a misleading complete list: retain the learned recipe with requirements unknown. Raw links/tooltips/private IDs are not stored.

Canonical stored dates come from capture game seconds at the GameSync boundary. Add `normalizeWorkshopCapture(value,sourceAt)` to convert finite Unix-second observation times or existing canonical times, reject collection dates newer than their enclosing source save, then strict-validate. Readiness validator delegates to validateWorkshop; GameSync normalizes only captured workshop timestamps before existing profile validation. Backup/Store paths remain strict canonical ISO. Missing is unknown; complete true with an empty array is known empty. Incomplete collection counts are lower-bound observations, never full inventory/recipe totals or zero shortfall proof.

Main-owned captured `readiness` remains protected by existing ordinary-save merge. Explicit backup import/GameSync are the only evidence-introduction boundaries. New workshop fields stay out of existing automatic AI context. Private goals/journeys remain private. Old backups/snapshots without workshop remain valid. Retain the existing 1MiB decoded addon payload/transport limits.

## Native collection

Implement bounded independent skills/recipes/material helpers inside existing BackstageForever.lua: no new managed addon file. Scan <=100 skill lines; current owned profession metadata only. Query <=100 known recipe spells total and <=20 reagent slots per recipe. Resolve professionID from returned metadata, not by equating it to skillLineId. RecipeInfo identity/learned must agree; no linked/guild recipes. If a view is explicitly linked/guild or ownership is ambiguous, recipes are unavailable/partial. Basic, required, single-item, fixed-quantity slots may yield exact requirements; any required alternate/variable/currency/unknown slot makes that recipe's requirements unknown. Optional slots are excluded, not required. Do not mistake all profession spells for recipes.

Scan bags0..4, <=256 total slots and <=256 aggregated unique item IDs, using public C_Container APIs. Aggregate stack counts, sorted by item ID, mark incomplete on limits/unreadable slots. No bank/reagent-bank/account/guild/mail storage, item links or purchases. The scope label explicitly states backpack plus four bags; absence from partial data is unknown. Zero total capacity is not a complete empty inventory observation.

Use per-collection capture dates and ensure the enclosing character/save updatedAt is not earlier than any collection observedAt, including a second boundary crossed during capture. A cached recipe collection retains its original date rather than receiving a new bag-only timestamp. Cache recipe results only for the current identity/build/session; invalidate on login/logout/identity/build/skill/recipe changes and never inherit another character's view. Recipe APIs are not polled again for every bag-only capture; material facts follow existing coalesced bag events. Add safely registered skill/trade-skill events; no new always-running timer. Missing/protected/failed optional workshop collection must not remove otherwise valid character/quest/XP/bag facts or turn the native plan into indefinite waiting. Error/secret values remain unknown, never unwrapped.

Raise the existing bounded Lua JSON decoder depth from8 to12 for the new nested reagent shape while retaining its node and byte limits. Add rich export→reload→capture roundtrip tests so another character is not lost by transport decoding. Shed optional workshop collections before shedding older quest/XP/history data when the export budget is exceeded; dropped data becomes unknown. Maintain five-file staging/repair and current native combat/lifecycle/source/phase geometry.

## Local planner, interface and actions

New pure `preparation.cjs`: `buildPreparation(state,profileId,{recipeId,crafts}={})` returns explicit selected-character source/coverage, observed professions/recipes/materials, equipment/bag facts, selected recipe and bounded shopping rows. crafts1..20 means craft attempts/batches, not a guaranteed number of output items. Verify recipe belongs to a currently observed owned profession, known learned recipe data has compatible source/time, and requirements are known. Aggregate required quantities; compute exact missing=max(0,required-have) only for complete applicable carried-bag observations, otherwise show have as a lower bound and missing null. Empty/unknown/ambiguous/changed profession cases must not say Ready to craft. Other characters' observations are separate dated facts and never subtracted automatically or advertised as transferable.

Trusted `preparationBrief(profileId,options)` (exact2 args, strict recipeId/crafts options) builds from latest state. Trusted `createPreparationJourney(profileId,options)` requires current active saved profile, known recipe requirements and exact quantities; creates one all-or-nothing manual checklist with existing applyJourneyAction/Store ownership. Manual steps have no quest or observed-completion metadata and do not auto-complete from inventory changes. Include only bounded recipe/reagent facts, not other-character/private notes. Known requirements with partial or missing carried counts may still create useful manual checks of total required quantities, explicitly saying carried supply is incomplete/unknown; do not call these exact missing/purchase quantities. Complete applicable inventory may use computed shortfalls, with already-satisfied materials shown as manual verification rather than invented game completion. Empty/unknown recipe requirements cannot become a false completed checklist. Main-owned IDs/dates and existing reset/trust/queue guards apply. Return latest state, journeyId. No AI or game action.

Add Preparation navigation and a focused workshop renderer/styles with original class/faction artwork, illustrated recipe/reagent cards, source dates, coverage badges and simple recipe/crafts controls. Selection preferences are local per-character and reset/import safe; they never overwrite game evidence. Defaults pick a useful known recipe where available; an unsupported/manual/empty character still has a clear attractive state and can use Company manually. Refresh derived shortfalls after saves without stealing focus/range or interrupting pointer/native-select lifecycles. One explicit Add shopping checklist uses existing mutation queue/epochs, pending guard, visible retry and Company navigation. All dropdowns remain dark/readable. Explain actions, if provided, create a bounded editable draft only; no inventory or goals added to automatic AI sharing.
