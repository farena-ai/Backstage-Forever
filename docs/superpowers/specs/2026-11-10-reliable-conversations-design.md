# Reliable in-session conversations — design

Binding umbrella: 2026-11-10-guided-companion-series.md. This task fixes the visible-conversation/standalone-request mismatch without enabling persistent model sessions or automatic memory sharing.

## State and request ownership

Add a focused main-owned ConversationSession service in src/core/companion-conversation.cjs and shared request integration in src/core/companion-service.cjs (or equivalent focused module; keep main wiring small). Retain the existing CompanionRequest cancellation/native settlement contract and MemoryService's reviewed exchange flow. Session stores at most six completed question/answer pairs in process memory, with original questions <=12,000 characters and replies <=100,000; provider context uses at most 6,000 characters of bounded prior conversation within the EXISTING total 12,000-character augmented prompt cap. Current original question and explicitly selected memory are preserved verbatim. Omit/clip old context with an explicit truncation indicator; never create invalid JSON or cut an active current question. No disk transcript, profile schema, export/checkpoint/diagnostic inclusion, remote session resume or paid helper call.

Prior exchanges are labelled untrusted conversation; previous AI answers never establish mechanics, quest proof, paths or eligibility. Context contains original user questions and completed replies only; Stop/failed/stale/refused requests do not become successful model history. Local saved-memory draft keeps the ORIGINAL current question, not a concatenated transcript.

Owner key includes active profile ID, selected provider/model/endpoint/auth mode and opaque source identity plus explicit source-root/replacement epoch. Per-request sharing choice and sorted explicit memory IDs are scope boundaries: a sharing or memory-selection change starts a fresh conversational context. In particular, an answer that used saved memory must not be automatically resent on a question whose memory selection is empty. Same explicitly selected memories may continue only when independently selected again. Normal unselected-memory questions continue naturally. These boundaries also reset the visible conversation/notify the player, so no invisible prior data is transmitted.

Character switch (including away/back), provider/auth/key changes, source root/connect/disconnect, Clear conversation, renderer reload/destroy/gone, import/reset/recovery replacement clear session ownership even if restored public IDs match. Ordinary public snapshot updates for the same source retain completed conversation as historical text; CURRENT approved facts win. Ordinary private-note/goal edits never add their text or needlessly clear unchanged conversation. Ordinary app-page navigation cancels in-flight work and retires reviewed voice/memory tokens, while completed same-owner conversation remains visible and available when returning. Request acceptance/commit must use both existing context generation and session owner/generation; no canceled or late response can repopulate history after Clear/replace/provider switch. Main serializes local and provider work through the existing request owner; renderer cannot submit forged assistant turns or history.

## Public interfaces

Legacy backstage.ask(input) retains string return for compatibility but uses the SAME shared main-owned pipeline/history/privacy as the new endpoint. Add backstage.askCompanion(input) with the same exact input keys {provider,prompt,profileId?,shareProfile,memoryIds?}, returning bounded {text,kind,conversation:{usedTurns,omittedTurns,resetReason?}}. kind initially ai or scope; later local travel integration may add travel without changing renderer-controlled input. No model/key/source-owner IDs in returned conversation metadata. Both endpoints enforce exact arity/keys and current identity. Add backstage.clearConversation() (zero args) to cancel active work, retire the latest memory draft and clear main session; no deletion of saved character memory. A small read-only conversationStatus() may expose bounded counts/notices only if needed, never arbitrary history injection. No new provider billing modes or fallback.

Every API/Ollama Cloud/local Ollama/ChatGPT subscription/Claude official-tool transport receives the SAME composed bounded prompt. Preserve current permanent Forever instruction, context whitelist, store:false, no-tools/no-MCP/no-hooks/no-session-persistence CLI boundary and cancellation/timeout/output caps. Compose session history once in main; adapters must not each rebuild a different memory budget. Existing lower-level callers with no session keep their old behavior.

For a direct game correction such as 'This is for WoW Forever, not retail', retrieval can retain the prior original question as the evidence query, labelled as a continuation. General prior context is available to the model. Do not concatenate unrelated previous requests into every retrieval query or promote old assistant text into evidence. Define a pure conservative continuation helper that returns the most recent original user question only for unambiguous correction wording; the travel task will own explicit structured trip intent.

## Player experience

The chat says plainly that recent messages accompany follow-ups; permanent saved memory remains separate and per-question. Keep provider/billing/character-sharing visible. Clear conversation actually clears main-owned context, not just the displayed messages. Preserve successful text after request failure, editable recovery, Enter/Shift+Enter/IME semantics, no auto-send, old voice/memory controls and cancellation. Prefer new askCompanion when available; an explicit compatibility fallback may call old ask in older synthetic bridges. Preserve current instruction scope and keep private notes/goals/keys/paths out of all automatic payloads.

Same-owner navigation should retain completed visible conversation rather than clearing it merely because the main page changes. Sharing/memory scope and character/provider/root/replacement boundaries clear both UI and main ownership. Retaining same-owner text is process-local; closing/reloading starts fresh. Clear in-flight work uses existing native shutdown settlement, so a second Claude process cannot start before the old one has closed.
