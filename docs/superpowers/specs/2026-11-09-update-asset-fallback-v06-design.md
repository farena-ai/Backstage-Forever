# Official asset-route recovery for BF 0.6

The original updater can discover 0.5 but sometimes receives HTTP 504 for its standard GitHub release-download route. Task1 adds safe retries and diagnostics; subsequent native checks still exhausted that route. The parent independently requested the public manifest through GitHub's documented REST asset endpoint, anonymously with Accept application/octet-stream: API302, approved release-assets host200, 555 bytes, valid pinned Ed25519 signature. Full native installer proof is recorded separately before production implementation is authorized by this plan.

Use the official fixed-repository REST asset route as a bounded transient-failure fallback. This is a transport alternative for the same signed bytes, not a new source of release trust. Keep normal browser-download URL first. Compared with repeating a failing redirect route, the API can obtain fresh asset delivery; compared with an arbitrary mirror, it preserves repository ownership and the existing cryptographic checks. No GitHub token, login, cookie or new user setup is permitted.

## Binding requirements

- Initial API asset targets must be exactly HTTPS api.github.com/repos/farena-ai/Backstage-Forever/releases/assets/<positive safe integer>, with no credentials, port, query, fragment, escaped path or extra segments. Build this URL from a validated numeric asset ID, never accept a URL supplied by metadata/renderer. Discovery remains its existing exact fixed API URL.
- Select asset IDs only from the already selected newest release's assets whose exact name and browser_download_url match the expected manifest or signed installer URL. Never hardcode the current 0.5 asset IDs into production. Missing/invalid IDs disable this fallback without invalidating normal valid releases.
- Keep the signed manifest URL exactly the existing expected browser-download URL. Verify its signature, version/tag/repository binding, installer SHA256 and size unchanged. GitHub metadata and an asset ID cannot authorize an installer. Invalid signature/hash/size/path errors are permanent and must not trigger a second-route bypass.
- Preserve the total three-attempt budget for each discovery/manifest/download operation; do not multiply it by route. After a retryable first standard-route failure, subsequent fresh attempts may use the validated alternate asset route. Each installer attempt has a fresh file/hash and mandatory cleanup-before-backoff. No partial reuse, Range resume, TLS bypass or Windows-security changes.
- API binary responses may be200 or redirect302. Redirects must use the existing approved public asset hosts; an arbitrary API endpoint, foreign repository, HTTP target or unapproved redirect must fail. Accept application/octet-stream for asset requests. Anonymous requests only. Never alter signed CDN query strings or print them. Existing fresh initial redirect handling may be reused safely.
- Preserve previous verified ready installers, cancellation/epochs, safe Windows cache behavior, bounded diagnostics and truthful failed-newer status. No UI changes beyond existing Retry/Open Releases are required.
- Test first: standard504 then authenticated API recovery; both manifest and installer alternate IDs; missing/mismatched IDs; strict API path and redirect refusal; three total attempts; invalid signature/hash/size never fall back; cancellation/partial cleanup/previous-ready regression coverage. Use public/synthetic metadata only.
- Prove the resulting production implementation through actual isolated Electron networking/crypto/cache, including an interrupted download recovery when the network permits. Full public installer hash/size/signature verification remains mandatory. No installer execution or actual user/game data changes.

Read-only research and production tests must distinguish a fully verified download from a completed installed upgrade. Report transient upstream failures honestly. Update recovery docs with the official fallback and measured evidence only after it is implemented and reviewed.
